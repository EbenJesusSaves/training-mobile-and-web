# Architecture and key decisions

This document explains the important choices in RailPass, why they were made, and when a different
choice would make sense. The training course (`training/`) builds on these explanations.

## 1. System overview

```
┌──────────────┐   HTTPS/HTTP JSON    ┌──────────────────────┐    SQL     ┌──────────────┐
│ Expo app     │ ───────────────────▶ │ NestJS API (/api)    │ ─────────▶ │ PostgreSQL   │
│ (passengers) │                      │  auth · stations ·   │            │ (Docker vol) │
└──────────────┘                      │  journeys · bookings │            └──────────────┘
┌──────────────┐                      │  admin/*             │   SMTP     ┌──────────────┐
│ Vite app     │ ───────────────────▶ │                      │ ─────────▶ │ Mailpit (dev)│
│ (staff)      │                      └──────────────────────┘            └──────────────┘
└──────────────┘
```

- One REST API serves both frontends. Passenger endpoints live at `/api/*`; staff endpoints at `/api/admin/*`.
- Every route requires a bearer token unless marked `@Public()`; staff routes add `@Roles('STAFF')`; booking
  endpoints are `@Roles('PASSENGER')` and always filter by the signed-in user (other users' bookings return 404).
- Errors always have the same shape: `{ statusCode, code, message, details? }`. Validation errors use
  `code: 'VALIDATION_FAILED'` and `details.fieldErrors` keyed by field path, so forms can show messages inline.

## 2. Data model (Prisma, `backend/prisma/schema.prisma`)

| Model | Purpose |
| --- | --- |
| `User` | Passenger or staff (`role`). Passwords are hashed with Node's built-in `scrypt`. |
| `PasswordResetToken` | Hashed 6-digit code, 15-minute expiry, max 5 attempts, single use. |
| `Station`, `Route` | Network. A route is a directed station pair with default fares. |
| `Journey` | A scheduled departure on a route: train number/name, service code (IC+, IC, R), times, status (`SCHEDULED`/`DELAYED`/`CANCELLED`), fares per class. |
| `JourneyCar` | Capacity: car number, class, number of 6-seat compartments. Seats are derived, not stored. |
| `AddOn` | Extras such as luggage, with staff-editable prices. |
| `Booking` | Reference (`TRN-YYYY-NNNNNN`), trip type, status (`CONFIRMED`/`CHECKED_IN`/`CANCELLED`), totals, `paymentMethod = SIMULATED`. |
| `BookingPassenger`, `BookingSegment`, `Ticket` | Who travels, on which journey(s) and class, and in which seat. A ticket has a unique `ticketCode`. |
| `SeatReservation` | Exists **only while a seat is held**. Unique on `(journeyId, carNumber, seatNumber)`. |
| `BookingAddOn` | Chosen extras with the unit price at booking time. |

Money is stored as integer pesewas (`…Cents`) to avoid floating-point errors. Times are stored in UTC.

## 3. Decisions

### Preventing double-booked seats
**Chosen:** a separate `SeatReservation` table with a unique index. Booking runs in a transaction; if two
requests race for the same seat, PostgreSQL rejects the second insert and the API returns `409 SEAT_TAKEN`
with the conflicting seats. Cancelling deletes the reservations (tickets stay for history).
**Why:** the database guarantees correctness under concurrency without application locks or a cache.
The e2e test `backend/test/booking-flow.e2e-spec.ts` fires two simultaneous bookings and asserts exactly one wins.
**Alternatives:** `SELECT … FOR UPDATE` on a seat row (needs every seat stored), or temporary "holds" with expiry
(better UX for long checkouts; more moving parts — a good extension exercise).

### Server-side pricing
**Chosen:** clients send *selections* (journeys, class, seats, extras), never prices. `calculatePrice()`
(`backend/src/bookings/pricing.ts`) is a pure function used by both `POST /bookings/quote` and `POST /bookings`.
The mobile app shows a live *estimate* while choosing seats and the server quote on the review screen.
Unknown request fields are rejected (`forbidNonWhitelisted`), so a tampered `totalCents` is a 400.

### Simulated payment
No payment provider was specified, so "Confirm & Pay" takes no payment. The apps don't show a notice about this.
It still creates a real booking with server-calculated totals (`paymentMethod: "SIMULATED"`). No card details are collected.

### Time zone
The sample network runs on GMT (Africa/Accra, UTC+0, no daylight saving). Search dates are UTC days and
the apps format times from UTC fields (`mobile/libs/format.ts`). This keeps the teaching code simple; supporting
several time zones would mean storing a station time zone and formatting with it (a course discussion point).

### Ticket barcode (PDF417) generated by the API
The reference ticket shows a wide 2-D barcode. A PDF417 encoder for React Native costs ~2 MB of JavaScript
(bwip-js), so the API generates the symbol (`backend/src/bookings/barcode.ts`) and returns a ~1 KB module
matrix with each ticket. The app draws it as a single Skia path; the PDF embeds the same matrix as SVG.
The payload `RAILPASS|<reference>|<ticketCode>` can be searched in the dashboard.

### Authentication and password reset
JWT bearer tokens (7-day expiry, no refresh token, to keep the training code small; refresh tokens are an extension).
The mobile app stores the token in the device keychain via `expo-secure-store`; "Remember me" off keeps it in memory only.
Password reset emails go to **Mailpit** (a local SMTP inbox in Docker) and the code is also printed in the API log when
`LOG_RESET_CODES=true`. Responses never reveal whether an email exists.
Social sign-in buttons from the reference were **omitted**: no OAuth configuration exists, and fake buttons would mislead.

### Mobile state and data fetching
- **Zustand** stores: `session-store` (token + user, persisted), `preferences-store` (theme, onboarding, dev API URL),
  `booking-draft-store` (search and selections; only the last route is persisted). Components subscribe with
  selectors (or `useShallow`) so unrelated changes don't re-render them.
- **Server data** is fetched with a ~100-line hook, `hooks/use-api-query.ts`: cache-then-revalidate, abort on unmount,
  ignore out-of-order responses, refetch on focus, optional polling. The seat map polls every 20 s and reconciles
  seats that were taken in the meantime. React Query was not added because the required mobile stack lists Axios +
  Zustand and the needs are modest; the course compares this hook with TanStack Query used in the dashboard.

### Dashboard state
Redux Toolkit holds client state (session, colour-scheme preference, UI preferences); TanStack Query holds all
server state (cache, refetch intervals, mutations with targeted invalidation). Server data is never copied into Redux.

### Styling and design tokens
All design values live in constants (`mobile/constants/*`, `dashboard/src/shared/constants/*`), mirrored in
`docs/design-tokens.md`. Components never hard-code spacing, sizes, colours, radii, font sizes, durations or
breakpoints. The mobile theme object carries only colours (the only thing that changes with the theme);
static scales are imported directly.

### Skia usage
Skia draws what native views can't do well: the background glow, the journey timeline with its train glyph,
the train-car seat map (car body, compartments, hatched unavailable seats, selection pulse), the ticket silhouette
with notches, the PDF417 barcode, the illustrated travel scenes and the booking-confirmed animation. Interactive
elements stay as native `Pressable`s layered on top, so screen readers, focus and hit areas keep working.
Animations run on the UI thread through Reanimated shared values and are skipped when *Reduce Motion* is on.

## 4. Deviations from the MyMTN reference guide

| Guide | RailPass | Reason |
| --- | --- | --- |
| Bare React Native + React Navigation | Expo + Expo Router (`app/` routes) | Required stack; file-based routes with typed links |
| Restyle | `StyleSheet` + typed constants | Fewer dependencies; tokens are plain TypeScript that both apps mirror |
| MMKV | `expo-secure-store` | Works in Expo Go; data is tiny (token, preferences); stored in the keychain |
| React Query on mobile | Small `useApiQuery` hook + Zustand | Required mobile stack (Axios + Zustand); contrasted with TanStack Query in the dashboard |
| `I`-prefixed interfaces (optional) | No prefix | The guide marks it optional; we use plain PascalCase consistently |
| Detox E2E | Not set up | Out of scope; Maestro/Detox are suggested course extensions. API flows are covered by backend e2e tests |
| Folder names `screens/`, `contexts/` | `features/*/screens`, `store/` | Requested structure: routes in `app/`, implementations in features |
| ESLint + Prettier everywhere | Backend and dashboard use oxlint (their generators' defaults); mobile uses `expo lint` (ESLint) | Each tool is the default of its official template |

Kept from the guide: kebab-case file names, PascalCase components, `use…` hooks, import grouping
(external → components → hooks → utilities → constants/types), component section order
(hooks → derived state → handlers → effects → render), conventional commits, PR template ideas, Jest/RNTL.

## 5. API overview

| Method & path | Who | Purpose |
| --- | --- | --- |
| `POST /auth/register`, `POST /auth/login`, `GET /auth/me` | public / any | Sessions |
| `POST /auth/password/forgot`, `POST /auth/password/reset` | public | Development email reset flow |
| `PATCH /me`, `POST /me/password` | signed in | Profile |
| `GET /stations`, `GET /stations/:id` | public | Station list; detail with destinations and next departures |
| `GET /journeys/search?originId&destinationId&date&passengers&sort` | public | Results with per-class fares and availability |
| `GET /journeys/:id`, `GET /journeys/:id/seats` | public | Journey and seat map (taken seats per car) |
| `GET /add-ons` | public | Extras |
| `POST /bookings/quote`, `POST /bookings`, `GET /bookings?scope`, `GET /bookings/:id`, `POST /bookings/:id/cancel` | passenger | Booking flow |
| `GET /admin/overview` | staff | KPIs, 14-day series, next departures, busiest journeys |
| `GET/POST/PATCH /admin/stations`, `/admin/routes`, `/admin/add-ons` | staff | Network and fares |
| `GET/POST/PATCH /admin/journeys` (+ `GET /admin/journeys/:id`) | staff | Timetable, status, capacity (with booked-seat protection), manifest |
| `GET /admin/bookings`, `GET /admin/bookings/:id`, `PATCH /admin/bookings/:id/status` | staff | Search, details, check-in/cancel |
| `GET /admin/passengers`, `GET /admin/passengers/:id` | staff | Passenger lookup |

Full request/response schemas: http://localhost:3000/api/docs.
